## 2. 画面布局

沿用 1280×720 横向画布和深色背景：

```text
┌─────────────────────────────────────────────────────────┐
│ 轨迹 ID / 运行版本                       程序状态 / 来源 │
├───────────────────────┬─────────────────────────────────┤
│                       │ 当前阶段：S1 / S2 / S3 / S4      │
│   原始视频等比放大    │ 当前原帧号、总帧数、源相对时间  │
│   保留完整视野        │ 四阶段名称及各自帧范围          │
│                       │ 三个候选结束帧、节点 ID、时间   │
│                       │ 待复核原因、模型/人工标签来源   │
├───────────────────────┴─────────────────────────────────┤
│ 四阶段彩色时间线 + 三个边界标记 + 当前播放位置           │
└─────────────────────────────────────────────────────────┘
```

- 原始画面沿用左侧约 560×560 的区域，等比缩放居中；文字和时间线绘制在原画面外侧，不遮挡夹爪与衣物，不裁掉源视野。放大仅用于查看，不声称增加源图细节。
- 右侧突出当前阶段，列出四段闭区间，当前行随视频播放高亮。命名对应新契约：S1 单侧叠入（含前期准备）、S2 双侧长条、S3 小方块、S4 移走与收尾。
- 保留旧配色：S1 青色 `#42b7cf`、S2 紫色 `#9c8cf5`、S3 橙色 `#efb85f`、S4 绿色 `#64c396`；未知为灰色。
- 显示原始帧号 `frame / (N-1)` 和相对源起点秒数。边界列表固定三个槽位，缺失显示“未确定”，不将后续槽位前移。
- 底部显示彩色阶段时间线、三条边界线和移动游标。边界线位于 `b` 与 `b+1` 之间；按帧等宽绘制时位置为 `(b+1)/N`，当前帧游标为 `(i+0.5)/N`。
- 状态至少区分 `complete`、`needs_review`、`execution_error`，另显示标签来源。`complete` 仅表示候选链完整，不写成“人工通过”。
- 中文需使用可显示中文的字体并验证；没有合适字体时使用明确的英文标签，避免输出方框或缺字。

视频始终按源时间正序播放、保持原速。stage3→2→1 是模型调用顺序，不改变导出视频的播放方向。倒序调用明细保存在 `trace.jsonl`；画面不强行制造逐帧活动标签。

## 3. 标签与数据适配

导出输入为原视频、经核验的 PTS 轴、新 `result.json` 和明确选择的标签来源。导出是纯本地结果展示，不再次调用 VLM、不重新选择边界。

默认显示模型候选：三个槽位均有效时根据 [boundary.md](../boundary.md) 展开四阶段。即使结果因 `uncertain` 带 `needs_review`，仍可显示完整候选划分，但必须保留待复核状态和“模型候选”标识。

缺边界或顺序非法时遵守新库规则：阶段数组和主时间线全部显示未知；已经选中的节点仍在边界列表和时间线标记中显示。**不要照搬旧 `candidate_layout` 的部分区间自动填充行为。** 用户后续要求展示部分阶段时，再单独调整统一契约。

人工标签存在时，可显式导出带 `reviewed` 后缀的视频，并展示复核来源；不要在同一个默认候选视频中无提示地替换成人工答案。导出过程不得写回或改变 `stage_candidates.npy`、`stage_reviewed.npy`、模型结果与人工记录。

适配时删除对旧 `interval_observations`、`intervals.json`、`participant_arms`、`task_type/applicable` 的依赖。第一版不展示旧的 `Action (model)` 全区间活动行，也不把未评估的 stage4 终态显示为成功或失败；需要显示时写“未评估”。数据清单已限定叠衣服。

## 4. 编码与时间轴

- 输出 `.mp4`，H.264（`libx264`）、`yuv420p`、1280×720、`+faststart`。首轮沿用旧参数 `crf=20`、`preset=veryfast`；参数写入导出记录。
- 逐个源解码帧合成一个输出帧；保留全片，不抽成推理用的稀疏图、不剪短、不改变播放速度。
- 保持源帧率与相对 PTS；输出起点可归零，原视频非零起始 PTS 必须正确减去。优先复用旧 `time_base=1/90000`，逐帧显式赋值，不靠名义 FPS 重建全部时间戳。
- 第一阶段 10 条均为 20 FPS，清单顺序帧数为 681、573、595、483、786、544、620、540、781、965，合计 6568 帧；仍以实际解码与冻结清单核验为准。
- 沿用旧导出器对无音轨源视频的支持范围；遇到音轨应明确报告暂不支持或实现保留，不能静默丢弃。
- 写入 `.part.mp4`，成功完成编码并通过验证后才发布最终文件；同名结果存在时不覆盖，使用明确的新导出名称/版本。失败保留原因和临时文件，不能在汇总中报成功。

## 5. 产物与记录

```text
runs/<run_id>/
  videos/
    <episode_key>__candidates.mp4
    <episode_key>__candidates.json
    exports.json
  reports/
    video_verification.json
```

每个视频同名 JSON 保存：源视频摘要、结果摘要、标签来源及摘要、导出器版本/摘要、三个边界槽位、画面上的阶段区间、状态、尺寸、编码参数、源/输出帧数、PTS 检查结果和输出文件摘要。人工版用 `__reviewed` 后缀区分。

`exports.json` 汇总全部 10 条视频位置与成功/失败；`video_verification.json` 保存实际重新解码的检查结果。某条结果不完整但原视频可读时仍应导出未知/待复核视频；源视频不可解码时记录失败并修复，不能伪造空视频或把少于 10 个有效视频标为第一阶段交付完成。

## 6. 验证与验收

实现后先做对应的离线导出测试，再导出第一阶段 10 条实际复核视频：

1. 重新解码输出，逐帧核对数量与相对 PTS，检查 H.264、yuv420p、1280×720。时间误差上限为编码 time base 的一个 tick 加数值容差，记录实测最大误差，不能只检查文件能打开。
2. 使用含非零起始 PTS 的短视频测试归零映射，并确认输出无丢帧、无额外补帧。
3. 测试边界帧归前段、下一帧换段、缺槽位不补标签、冲突边界全未知、导出不修改任何标签及重复导出不覆盖。
4. 000543 实际结果仍为 400/485/562 时，查看 399/400/401、484/485/486、561/562/563 帧：高亮与时间线必须分别在 401、486、563 切换。确认 562 帧不会因左爪闭合被展示成未知。
5. 抽看每条首帧、末帧和边界附近，确认源画面、文字、状态与时间线可读；未知结果的视觉提示不能伪装成完整划分。

旧导出器通过过的检查只说明旧实现。新接口迁移后的测试与 10 条视频重新解码结果必须单独记录。
